# Інструкція з реалізації frontend сервісу прогнозування ціни ноутбуків

## 1. Завдання для чату реалізації

Реалізуй frontend сервісу, який прогнозує ціну ноутбука за комплектуючими та характеристиками, введеними користувачем. Використовуй цю інструкцію як специфікацію інтерфейсу, поведінки та інтеграції з backend.

Перед початком переглянь наявний проєкт, `options.json`, маршрути FastAPI, схеми запитів і відповідей та доступні аналітичні дані. Збережи сумісність з наявним backend. Не вигадуй поля форми, назви моделей, метрики, результати чи причини помилок.

Якщо потрібних даних або контрактів немає, підготуй незалежні частини інтерфейсу та уточни лише відсутні відомості, які блокують інтеграцію. Не підмінюй реальний прогноз випадковим числом чи демонстраційними даними.

## 2. Технології та маршрути

- Frontend: HTML5, CSS3, JavaScript. Базовий варіант — без frontend-фреймворків і без обов’язкового етапу збірки.
- Backend: Python, FastAPI.
- Головна сторінка «Прогноз»: `http://localhost:8000/`.
- Сторінка «Аналітика»: рекомендований маршрут `/analytics`; звірити з backend.
- Сторінка Swagger: `http://localhost:8000/docs/`.
- API прогнозу, джерела аналітики та спосіб отримання `options.json`: визначити з проєкту. Не припускати, що файл доступний за URL `/options.json`.
- Для внутрішніх переходів і API використовувати відносні адреси або централізоване налаштування базової адреси, щоб інтерфейс працював поза localhost.
- Мова інтерфейсу — українська.

## 3. Візуальний стиль і загальні компоненти

### 3.1. Стиль

Основний стиль — кібер та мінімалізм. Палітра: зелений, чорний, фіолетовий, білий. Використовувати чисту композицію, читабельну типографіку, достатні відступи та помірні акценти. Не перевантажувати сторінки сяйвом, рухом або декоративними деталями.

Кольори, фон, текст, рамки й акценти визначити через CSS-змінні. Кольори станів мають залишатися зрозумілими в усіх темах; стан не повинен передаватися лише кольором.

### 3.2. Компонент `SiteHeader` — закріплена навігація

На головній навігація розташована зверху праворуч. Під час прокручування вона залишається зверху екрана. На власних сторінках сервісу зберігати однаковий вигляд, склад елементів і налаштування.

Склад:

- Посилання «Прогноз» на `/`; на головній може бути назвою сервісу або позначеним активним пунктом.
- Посилання «Аналітика».
- Посилання «Swagger».
- Кругла кнопка `ThemeSwitcher` для вибору теми.
- Кнопка `MotionToggle` для увімкнення та вимкнення анімацій.

Передбачити місце під висоту закріпленої панелі, адаптивне розміщення пунктів та відступи для якірних переходів (`scroll-margin-top` / `scroll-padding-top`). Навігація не повинна перекривати заголовки, форму, повідомлення або розділи після переходів.

### 3.3. Компонент `ThemeSwitcher` — теми

Підтримати декілька варіантів. Реалізувати три теми: «Темна», «Світла», «Фіолетова». Базово відображати сайт у Темні темі

Кругла кнопка відкриває компактний список тем з позначенням поточної. Зберігати вибір локально та застосовувати на головній і в аналітиці, зокрема після перезавантаження. Перший запуск може враховувати системну світлу/темну тему. Забезпечити керування клавіатурою та зрозумілу доступну назву кнопки.

### 3.4. Компонент `MotionToggle` — контроль руху

Кнопка має явно показувати поточний стан. Зберігати вибір локально між сторінками та перезавантаженнями.

У режимі без анімацій:

- Замість рухомого фону показувати статичну композицію з градієнтом і силуетами ноутбуків.
- Вимкнути анімацію заголовка, декоративні рухи, анімації появи форми та плавне прокручування.
- Зберегти видимість і працездатність усіх компонентів.

На першому запуску враховувати `prefers-reduced-motion`. На сторінці аналітики анімації відсутні незалежно від цього налаштування.
Базово анімаці увімкнена

### 3.5. Компонент `SiteFooter` — службова інформація

Розміщувати внизу головної та сторінки аналітики, у звичайному потоці документа.

Поля: «Автор», «Група», «Поточна дата», «Електронна пошта», «Номер телефону».

Автор, група та контакти задаються через єдине налаштування. До отримання реальних значень показувати нейтральне «Не вказано», не вигадувати особисті дані. Дату формувати автоматично, форматувати для українського інтерфейсу; вона має бути актуальною також при тривалому відкритті сторінки. Для заповнених контактів використати `mailto:` і `tel:`.

## 4. Головна сторінка «Прогноз»

### 4.1. Структура та переходи

Сторінка складається з трьох послідовних екранів і футера:

1. `HeroSection` — титульний екран.
2. `PredictionFormSection` — форма характеристик ноутбука.
3. `PredictionResultSection` — результат прогнозу або докладна помилка.
4. `SiteFooter`.

Екрани орієнтовно займають висоту видимої області з урахуванням навігації, але можуть збільшуватися за вмістом. Не обрізати форму або результати для примусового вміщення в один екран. Переходи між екранами реалізувати плавним прокручуванням, якщо рух увімкнений. Уникати примусового scroll snapping, який заважає заповненню форми.

### 4.2. Перший екран — `HeroSection`

По центру екрана розмістити:

- Назву сервісу — остаточна назва потребує уточнення; тимчасово «Прогноз ціни ноутбука».
- Короткий опис: «Вкажіть комплектуючі та характеристики ноутбука, щоб отримати прогноз його ціни».
- Кнопку «Перейти до прогнозу», що прокручує до другого екрана.

Фон — анімований градієнт. Поверх нього знизу вгору повільно рухаються легкі векторні силуети ноутбуків без виразних деталей. Можна використати SVG та CSS. Декор не перехоплює натискання, не заважає читанню та прихований від допоміжних технологій.

Заголовок також анімований: стримана поява або м’яка зміна акценту. Не використовувати різке мерехтіння. Для вимкненого руху передбачити завершений статичний вигляд.

### 4.3. Другий екран — `PredictionFormSection`

Заголовок: «Характеристики ноутбука».

Основний компонент `LaptopSpecificationForm` будується на основі фактичного `options.json` та узгоджується зі схемою запиту API. Для кожного поля визначити ключ, підпис, тип контролу, обов’язковість, допустимі значення, одиниці вимірювання та обмеження, якщо ці відомості наявні в джерелах.

Правила:

- Для полів зі списками варіантів використовувати випадаючі списки; для решти — відповідні текстові або числові поля.
- Обов’язкові й необов’язкові поля чітко позначити. Не вигадувати обов’язковість, якої немає у схемі.
- Якщо `options.json` містить лише допустимі значення, типи та правила отримати зі схеми backend або явно узгодженого відображення.
- Порожнє необов’язкове поле передавати як пропущене значення, `null` чи інше значення лише відповідно до API-контракту; не перетворювати автоматично на нуль.
- Відображувані підписи можуть бути українськими, але ключі та значення для сервера зберігати сумісними з API.
- Групувати поля за змістом, якщо це відповідає наявним даним; точний склад і назви груп визначити після читання `options.json`.
- Підказки та помилки розміщувати поруч із відповідними полями.
- Використати легку анімацію появи форми, яка не запускається повторно при кожній зміні значення.

Кнопка «Прогноз»:

- Перевіряє введені дані та відправляє запит на backend без перезавантаження сторінки.
- Не стирає введені значення після успіху або помилки.
- Під час запиту показує стан «Обчислюємо…» та блокує повторне надсилання.
- Після завершення знову доступна для наступного прогнозу.

Кнопка «Очистити»:

- Очищає всі заповнені користувачем поля, включно зі списками, та локальні повідомлення валідації.
- Повертає поля до порожнього стану з підказками вибору, не підставляє перший варіант автоматично.
- Має тип `button` і не відправляє форму.
- Рекомендована поведінка: очищення форми не видаляє останній успішний прогноз з аналітики; це окрема дія над полями введення.

Передбачити стани завантаження `options.json`, успішного завантаження та помилки з кнопкою повторної спроби. Не дозволяти прогноз із неповною або невалідною конфігурацією форми.

### 4.4. Третій екран — `PredictionResultSection`

Заголовок: «Результат прогнозу».

Початковий стан: «Заповніть характеристики ноутбука та натисніть “Прогноз”».

Успішний стан — компонент `PredictionSummary`:

- Прогнозована ціна як головний візуальний акцент.
- Валюта - гривні (UAN).
- Можливі межі прогнозу або інтервал прогнозу з поясненням того, що саме вони означають (брати з  "numeric_ranges" з `options.json`).
- Модель або моделі, які виконали прогноз.
- Час відповіді з одиницями вимірювання.
- Посилання «Переглянути аналітику».

Після успішної відповіді автоматично прокрутити до результату та коректно перенести фокус на його заголовок для клавіатурної навігації. За вимкненого руху перейти одразу.

Якщо API повертає кілька окремих прогнозів, показати кожну ціну з відповідною моделлю. Якщо повертається агрегована ціна, зазначити моделі-учасники лише за наявності цих даних.

Для часу відповіді бажано використати виміряний у браузері час запиту. Серверний час обчислення, якщо він є, показувати окремо з точним підписом, оскільки це різні показники.

Стан помилки — компонент `PredictionErrorDetails`:

- Угорі по центру видимої області показати коротке повідомлення помилки українською на червоному напівпрозорому фоні з маленьким хрестиком на початку зліва, щоб закрити повідомлення, нижче закріпленої навігації.
- На третьому екрані показати зрозумілий опис, причину, код HTTP  та прикладний код помилки, якщо їх надав backend.
- Для мережевого збою або тайм-ауту явно повідомити, що HTTP-відповідь не отримана; не вигадувати код сервера чи причину збою.
- Для помилок валідації показати також зв’язок із конкретними полями, якщо сервер передав відповідну інформацію.
- Не виводити необроблений HTML, секрети, traceback або службові внутрішні дані.
- Надати дії «До форми» та повторної спроби, якщо вона доречна.

Обов’язковий автоматичний перехід заданий лише для успіху. Рекомендована поведінка при помилці: залишити користувача біля форми, а в повідомленні додати посилання «Докладніше» на третій екран. Докладна помилка залишається доступною після зникнення короткого повідомлення.

Під час нового запиту попередній результат не має виглядати як відповідь на нові дані: показувати стан очікування або явне позначення попереднього результату. Після невдалої спроби третій екран показує поточну помилку; останній успішний прогноз можна зберігати окремо для аналітики.

## 5. Сторінка «Аналітика»

### 5.1. Загальна структура

Одна цілісна сторінка з аналітичними розділами, верхньою навігацією, внутрішнім змістом і футером. «Один великий екран» означає єдину сторінку, яка може прокручуватися за потреби; не стискати весь вміст до висоти дисплея.

Анімації відсутні, включно з анімаціями появи та плавним переходом між розділами. Верхня панель забезпечує переходи на «Прогноз», «Swagger» і зміну теми.

### 5.2. Розділи та компоненти

- `AnalyticsOverview` — «Як формується прогноз»: загальний механізм роботи, використання характеристик ноутбука, доступне пояснення обробки даних.
- `AvailableModels` — «Доступні моделі»: назви, призначення, характеристики та метрики якості, якщо вони відомі з backend або документації проєкту. Для метрик вказувати назву й одиниці; не вигадувати показники.
- `LatestPredictionAnalytics` — «Останній прогноз»: відображається лише за наявності успішного прогнозу.
- `AnalyticsContents` — внутрішня панель навігації з посиланнями на наявні розділи. Позначати поточний розділ; при переході заголовок залишається видимим під верхньою панеллю.

На широких екранах внутрішній зміст може бути бічною панеллю; на вузьких — компактним списком над розділами. Він не повинен перекривати контент або футер.

### 5.3. Стан до першого прогнозу

Показувати лише загальну інформацію про механізми формування прогнозу, доступні моделі та їхні характеристики. Не відображати порожні графіки, фіктивний прогноз або розділ із персональною аналітикою без даних.

### 5.4. Стан після успішного прогнозу

Окрім загальної інформації показувати дані останнього успішного прогнозу:

- Характеристики ноутбука, надіслані саме для цього запиту.
- Отриману ціну та валюту.
- Межі помилки або інтервал, якщо надані.
- Модель або моделі та доступне порівняння їхніх результатів.
- Час відповіді та, за наявності, серверний час обчислення.
- Час виконання прогнозу.
- Додаткові пояснення впливу характеристик чи інші аналітичні дані — лише якщо їх підтримує backend.

Графіки додавати лише тоді, коли є реальні дані й вони допомагають зрозуміти прогноз. Не генерувати ваги ознак або пояснення роботи моделі на frontend.

### 5.5. Передача стану між сторінками

Використати наявний механізм збереження стану проєкту. Якщо його немає, рекомендований базовий варіант — `sessionStorage`: зберігати останній успішний прогноз разом зі знімком вхідних характеристик і часовою позначкою. Це забезпечує доступ після переходу на аналітику та перезавантаження в поточній вкладці.

Невдалий запит не замінює останній успішний прогноз. Зміни форми після прогнозу не змінюють збережений знімок характеристик. Пошкоджені або несумісні збережені дані обробляти як відсутність прогнозу. Якщо сховище недоступне, інтерфейс не повинен аварійно завершувати роботу.

Довготривале збереження історії та синхронізація між вкладками не задані; не додавати їх без окремої потреби.

## 6. Swagger та переходи назад до сервісу

Не створювати окрему сторінку Swagger на frontend. Використати документацію, яку формує backend FastAPI, з описом його web-ресурсів.

У верхній навігації сервісу додати посилання на фактичний маршрут Swagger. Із самої документації мають бути доступні переходи «Прогноз» і «Аналітика».

Спочатку перевірити, чи backend уже додає ці посилання. Якщо ні, потрібна мінімальна інтеграція в шаблон/обгортку Swagger, сформовану backend, зі збереженням роботи документації та її інтерактивних запитів. Якщо зміни backend поза межами доступу, явно позначити цю залежність як незавершену, а не заявляти, що зворотна навігація реалізована.

Глобальне оформлення та перемикач тем для Swagger не є окремою вимогою: обов’язковими є доступ до документації та переходи назад.

## 7. Взаємодія з API та стани інтерфейсу

Виділити модуль роботи з API, який відповідає за серіалізацію запиту, перевірку статусу HTTP, обробку відповіді, мережевих помилок і часу очікування. Тайм-аут узгодити з реальною тривалістю прогнозу. Завжди завершувати стан завантаження після успіху, помилки або скасування запиту.

До інтеграції зафіксувати фактичні відповідності:

| Дані | Джерело, яке необхідно перевірити |
| --- | --- |
| Поля та варіанти форми | `options.json` |
| Обов’язковість, типи, обмеження | Схема запиту backend та метадані форми |
| Метод і маршрут прогнозу | Маршрути FastAPI / OpenAPI |
| Ціна, валюта, модель, інтервал | Схема успішної відповіді |
| HTTP-код, прикладний код, деталі | Фактичний формат помилок backend |
| Опис моделей та метрики | API аналітики або документація проєкту |
| Пояснення останнього прогнозу | Відповідь прогнозу або окремий endpoint аналітики |

Не додавати непогоджені API-маршрути. Якщо додаткової аналітики немає, показувати підтверджені дані останнього прогнозу та чесно позначати відсутні показники.

## 8. Адаптивність і доступність

- Підтримати мобільні, планшетні та настільні екрани без горизонтального прокручування основного інтерфейсу.
- Використати семантичні `header`, `nav`, `main`, `section`, `form`, `footer`, один головний `h1` на сторінку та послідовні підзаголовки.
- Усі поля мають видимі підписи; усі кнопки й посилання доступні клавіатурою, з видимим фокусом.
- Повідомлення результатів і помилок доступні допоміжним технологіям через доречні live-регіони або ролі.
- Текст читабельний на градієнтах та в кожній темі. Декоративні елементи не заважають взаємодії.
- Передбачити довгі назви комплектуючих, великі ціни та довгі повідомлення помилок.

Адаптувати до структури наявного проєкту, не перебудовуючи його без потреби:

- HTML-шаблони головної та аналітики.
- CSS для змінних тем, загальних компонентів, головної та аналітики.
- JavaScript-модулі для налаштувань теми й руху, побудови та валідації форми, API, відображення результатів, збереження останнього прогнозу й аналітики.
- Векторні декоративні ресурси або inline SVG для ноутбуків.
- Єдине налаштування назви сервісу, контактів, маршрутів і доступних тем.

## 10. Питання, які потрібно звірити з проєктом або уточнити

Ці відомості не надані в початковому описі. Спочатку шукати їх у проєкті, а вже потім ставити користувачеві конкретні запитання:

1. Остаточна назва сервісу.
2. Вміст і структура `options.json`, типи полів, обов’язковість та одиниці вимірювання.
3. Маршрути та формати API прогнозу, аналітики й Swagger.
4. Валюта, значення меж помилки та склад результатів для однієї або кількох моделей.
5. Джерело загальних описів моделей, їхніх характеристик і метрик.
6. Автор, група, електронна пошта та телефон для футера.

Запропоновані в цій інструкції маршрути, назви тем, спосіб збереження стану й поведінка очищення — базові рішення для реалізації, якщо вони не суперечать проєкту або подальшим вказівкам користувача.

## 11. Критерії приймання

- Головна доступна на `localhost:8000/`, має три екрани та футер.
- Верхня навігація працює, залишається доступною під час прокручування та не закриває вміст.
- Титульний екран має центральний заголовок і опис, градієнт та рухомі векторні ноутбуки; заголовок анімований.
- Теми перемикаються і зберігаються; режим без анімацій показує повноцінну статичну версію.
- Форма відповідає `options.json` та API-схемі, перевіряє введення й коректно обробляє необов’язкові поля.
- «Прогноз» не стирає поля, повторне надсилання під час запиту заблоковане; «Очистити» очищає всі поля.
- Успішний прогноз автоматично відкриває третій екран із ціною, доступними межами помилки, моделями й часом відповіді.
- Помилка викликає коротке верхнє повідомлення та залишає доступними докладні відомості на третьому екрані.
- До першого прогнозу аналітика містить тільки загальну інформацію; після успіху також показує дані саме останнього успішного прогнозу.
- Внутрішня навігація аналітики працює; анімацій на цій сторінці немає.
- Swagger використовує сторінку backend; переходи на документацію та назад перевірені.
- Футер містить усі п’ять службових полів, дата формується автоматично.
- Основні сценарії перевірені на вузькому й широкому екрані, з клавіатурою та з вимкненими анімаціями.
- Перевірені успіх, помилки валідації, відповідь із серверною помилкою та недоступність мережі; інтерфейс не залишається у стані нескінченного завантаження.

Після реалізації коротко повідомити, що зроблено, як запустити сервіс, які сценарії перевірено та які реальні залежності залишилися незавершеними.
